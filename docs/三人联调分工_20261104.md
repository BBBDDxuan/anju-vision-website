# 安居视界：三人一天联调分工

日期：2026-11-04
目标：一个电脑后端连接多部手机，统一接入实时摄像头和手机上传录像产生的危险告警。
排序：按预计任务量从大到小排列；不是开发先后顺序，三人应同时推进。

> 工作量为基于现有能力的规划估计，不是实测工时。手机端已有页面及部分业务接入，应先核查并复用；Firebase 条件、实际源码完整度和网络环境会影响排序。以下不代表功能已经完成或验收通过。

## 1. 当天交付范围

```text
实时摄像头 ─────────┐
手机 A 上传录像 ────┼→ 一个电脑后端 → GPU 小模型 → Qwen 复核
手机 B 上传录像 ────┘                      ↓
                                统一持久化告警与证据
                                          ↓
                                  手机 A / B / C
```

### 必须完成

- 手机只配置一个后端地址；后端内部复用的通知服务不暴露为第二个必填入口。
- 告警来源包含实时摄像头、手机上传录像，来源可区分。
- 多部手机可读取同一家庭的告警，一部确认处理后其他手机同步状态。
- 手机完成连接、上传、启动分析、查看进度、查看告警与证据、确认处理。
- 前台新告警提醒、稳定 ID 去重、点击通知进入正确详情。
- 用两部真手机、一个电脑后端完成真实业务验收。
- 完整工程、依赖、安装构建脚本和文档可从 GitHub 获取并重建。

### 条件性目标

后台、锁屏推送：第一小时确认 Firebase 客户端配置、服务端授权及手机运行条件，条件齐全后纳入当天交付。若条件不齐，明确记为未完成，不能用前台轮询通知替代后台推送验收。

### 当天不做

前端美化、模型训练、检测阈值优化、手机端模型部署、复杂多家庭账号体系、手机远程开关电脑实时 AI。实时监护仍先在电脑网页开启。实摄告警接入与手机实时画面预览分别验收，不将两者混为一项。

## 2. 工作量排序总览

| 排名 | 角色 | 预计任务量 | 主要原因 | 核心交付 |
|---|---|---|---|---|
| 1 | A：统一后端与告警中心 | 最大 | 两类来源统一、持久化、多手机状态、网络认证及推送接点 | 可被手机访问的统一后端与接口契约 |
| 2 | C：多手机通知与发布验收 | 较大，外部依赖最多 | Android 权限、去重、冷启动跳转、推送登记、后台送达与构建 | 通知模块、APK、真机验收记录 |
| 3 | B：App 业务与接口接入 | 相对较小，取决于现有接口复用程度 | 复用已有页面和业务代码，集中统一入口与数据流 | 完整真实业务链路与事件详情入口 |

分配建议：最熟悉电脑、摄像头和模型环境的人负责 A；最熟悉 Android 通知与构建的人负责 C；最熟悉现有 App 页面和数据层的人负责 B。姓名由团队填写，不沿用早期四人分工猜测本次人员。

## 3. 第一名：A——统一后端与告警中心

负责人：__________

### 任务

- [ ] 固定当天使用的后端版本、启动命令、电脑局域网 IP 和统一入口端口。
- [ ] 配置手机可访问的监听地址、主机白名单、认证及必要防火墙规则；不直接取消摄像头控制接口的本机限制。
- [ ] 核查现有录像上传、列表、分析任务、进度和证据接口，优先复用，不另起一套分析流程。
- [ ] 将实时摄像头确认告警与上传录像确认告警接入统一数据层；不能假设现有录像接口天然包含实摄告警。
- [ ] 告警持久化，保证来源、唯一 ID、发生时间、复核状态、处理状态和证据关系完整。
- [ ] 提供统一告警列表、详情及确认接口；同一条告警的多次确认幂等，多手机共享处理状态。
- [ ] 接入 C 提供的独立推送模块；推送失败不丢告警、不阻塞识别分析。
- [ ] 提供无敏感数据的接口样例和联调命令，标明接口已存在、需要适配或需要新增。

### 修改边界

负责后端主入口、路由、告警数据层、来源适配和网络配置。后端公共入口由 A 单人整合；C 只提交独立推送模块。A 不修改 App 页面或 Android 原生配置。

### 交付物与验收

- 一条明确的后端启动命令、连接说明及接口契约。
- 两种来源的真实告警记录与证据。
- 两部手机使用同一个地址读取同一条告警；一部确认后另一部同步为已处理。
- 记录手机无法连接时的错误分类，区分网络、认证、模型环境及摄像头配置。

## 4. 第二名：C——多手机通知与发布验收

负责人：__________

### 任务

- [ ] 第一小时检查 Firebase 条件并明确后台推送是否能纳入当天硬目标。
- [ ] 核查 Android 通知权限、通知渠道、总开关及设置跳转。
- [ ] 实现前台新告警通知，按稳定告警 ID 去重；首次同步历史列表不默认全部响铃。
- [ ] 点击通知进入 B 提供的统一详情入口，覆盖 App 已打开和冷启动两种情况。
- [ ] 条件齐全时接入 FCM：每个手机安装实例独立登记，token 更新、解绑不影响其他手机。
- [ ] 服务端发送与设备登记实现放在约定的独立推送模块，与 A 冻结调用接口后并行开发。
- [ ] 分别测试前台、后台、锁屏、权限关闭、重复事件和通知点击；断网场景记录实际行为，不承诺未经验证的补发。
- [ ] 负责 APK 构建、版本记录、安装和发布附件。

### 修改边界

负责通知服务、原生通知配置、Firebase 客户端配置、独立服务端推送模块及构建发布。App 公共入口和详情路由由 B 单人整合；后端公共入口由 A 整合。签名私钥和服务端凭据不提交 Git。

### 交付物与验收

- 可复用通知模块及其调用说明，独立推送模块和接入说明。
- 可安装 APK、版本信息及真机测试表。
- 同一条真实告警通知两部已登记手机；单部手机不会因列表刷新反复提醒。
- 后台/锁屏结果单列，未实现或未验证必须明确标注。

## 5. 第三名：B——App 业务与接口接入

负责人：__________

### 任务

- [ ] 核查现有源码已接入的能力，优先修复和复用，不重写已经可用的页面与数据层。
- [ ] 将连接设置统一为一个后端地址，完成检查连接和本机配置保存。
- [ ] 接入录像上传、取消、分析启动、任务进度与结果，按现有能力保留暂停/继续。
- [ ] 告警列表同时展示实摄和录像来源，详情显示正确证据与片内时间定位。
- [ ] 接入确认处理及多手机状态刷新，防止本机旧缓存覆盖服务端状态。
- [ ] 正确处理相对媒体 URL、断网、认证失败、加载中、空列表和上传失败。
- [ ] 向 C 提供新告警数据接点和按来源/告警 ID 打开详情的稳定入口；避免 B、C 各自轮询并重复通知。
- [ ] App 退出不取消已经交给服务器执行的分析任务；回到前台重新同步任务与事件状态。

### 修改边界

负责 App API 服务层、数据模型、业务状态、连接设置、页面和公共详情路由。App 公共入口由 B 整合。B 不修改后端业务、原生通知配置或发布签名。

### 交付物与验收

- App 真实数据业务链路与 API 接入清单。
- 连接、上传、分析、查看告警与证据、确认处理的真机操作记录。
- 不用模拟数据冒充真实识别结果，不能因网页可用就视为手机已接通。

## 6. 前 30 分钟：冻结协作契约

以下是需要统一的设计契约，不代表当前接口已经实现。A 负责主文档，B、C 当场确认。

| 项目 | 约定 |
|---|---|
| 基线 | 后端与 App 源码版本、Git 提交号、合并负责人 |
| 入口 | 一个根地址；真机不用 127.0.0.1 连接电脑 |
| 认证 | 访问令牌获取与请求头方式；密钥不进入样例 |
| 告警 ID | 全局唯一、跨来源不冲突、刷新及重启后稳定 |
| 来源 | live_camera / uploaded_recording，附摄像头 ID 或录像 ID |
| 时间 | 固定时区/格式；录像发生时间与片内偏移分开 |
| 状态 | 复核状态与处理状态分离；仅确认危险触发正式危险通知 |
| 证据 | 手机可访问的受控地址，不返回电脑磁盘路径 |
| 增量同步 | 分页/游标或去重规则；首次历史同步是否提醒 |
| 多手机 | 同一家庭共享告警；确认状态同步；设备登记不相互覆盖 |
| B → C | 新告警回调、详情跳转参数、谁负责拉取和去重 |
| A → C | 告警保存后调用推送；推送失败与重试责任明确 |
| 错误 | 网络不可达、401/403、模型未就绪、分析失败分别显示 |

开发时可使用明确标注的样例响应解耦，正式验收必须使用真实后端和真实事件。

## 7. 一天时间表与检查点

| 时间 | A | C | B |
|---|---|---|---|
| 0～0.5 小时 | 三人冻结版本、契约、文件归属、验收目标 |
| 0.5～2 小时 | 提供可访问后端及接口样例 | 检查 Firebase、跑通构建、通知权限 | 核查现有接入、统一连接设置 |
| 2～4 小时 | 打通两类告警、持久化与统一查询 | 通知去重与跳转；条件齐全则接后台推送 | 接入真实列表、上传、任务与详情 |
| 4～6 小时 | 联调后端、网络、推送调用 | 联调通知、真机安装 | 联调业务链路与多手机刷新 |
| 6～7 小时 | 三人使用一个后端、两部真机完成端到端验收 |
| 7～8 小时 | 仅修阻塞问题，冻结提交、生成 APK、更新 GitHub 与交接说明 |

检查点：第 2 小时至少一部真机连接检查成功；第 4 小时至少出现一条真实确认告警。不要最后一小时才首次合并。若 A 工作量超出，优先延后手机实时画面或远程控制等非必做项，不牺牲真实告警闭环。

## 8. 最终验收清单

- [ ] 两部真机通过同一个后端地址连接成功。
- [ ] 手机 A 上传录像，后端分析，手机 B 可以看到同一录像的授权结果。
- [ ] 录像确认告警可以在两部手机查看并收到提醒。
- [ ] 实时摄像头确认告警可以在两部手机查看并收到提醒。
- [ ] 手机 A 确认处理，手机 B 刷新后同步状态。
- [ ] 同一告警重复刷新不重复响铃，历史同步不批量误提醒。
- [ ] 通知点击进入正确详情，证据可加载。
- [ ] 前台、后台、锁屏分别记录结果；不混用验收结论。
- [ ] 权限关闭、认证失败、网络中断有明确状态。
- [ ] GitHub 全新拉取后按文档完成安装、启动及 APK 构建或安装。

## 9. GitHub 完整交付与协作规则

### 应包含

网页前后端、App 完整源码、模型权重、媒体工具、配置模板、依赖锁文件、安装/启动/构建脚本、接口契约、测试及实际验收记录。APK 可作为 GitHub Release 附件，并记录对应提交号。

### 不提交

沿用此前约束：不上传视频或分片；不提交真实 .env、API Key、RTSP 密码、Firebase 服务端私密凭据及签名私钥。通过团队安全渠道分发必要凭据。虚拟环境、缓存、历史数据库和推理运行目录不进入源码交付，提供脚本重建。

### 避免冲突

- A 独占后端公共入口与告警主流程；B 独占 App 公共入口和详情路由；C 维护独立通知/推送模块。
- 提前约定独立文件写入范围，不同时修改同一入口；优先使用各自分支、小步提交。
- 任何接口变更先同步契约，不在最后联调时临时更改字段。
- 每人提交交接说明：修改文件、启动方式、已验证场景、未完成项。
- 不把“代码已写”“构建成功”“模拟器通过”自动等同于真实业务和后台通知通过。
